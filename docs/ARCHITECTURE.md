# TetherRoll OTC — 자금 흐름 & 에스크로 아키텍처 명세 (SSOT)

> **문서 지위 (Document Authority)**
> 이 문서는 TetherRoll OTC 플랫폼의 **자금 흐름·에스크로·정산·접근제어에 대한 단일 진실 공급원(Single Source of Truth)** 이다.
> 스마트 컨트랙트, 백엔드, 프론트엔드, 그리고 향후 **코드 감사(audit)** 는 모두 이 문서에 정의된 규칙에 부합해야 한다.

> - 관리 주체: TetherRoll OTC (Wyoming LLC)

## 0. TL;DR (한 문단 요약)

A와 B는 두 가지 방식 중 하나로 OTC 거래를 한다. **대외적으로 표준처럼 보이는 방식은 "2-of-3 공동 멀티시그 에스크로"(Mode 1)** 이다 — A·B·법인이 공동 지갑을 만들고, 출금에는 키 2개가 필요하며, 평시에 법인은 자금에 손대지 않는다(비수탁). 내부적으로는 **"보증금 기반 하이브리드 에스크로"(Mode 2)** 도 존재한다 — 온체인 거래는 컨트랙트가 양측 자산을 보관해 원자적으로 동시 정산하고, 오프라인 거래는 양측이 USDT 보증금을 걸고 양쪽 다 '완료' 서명을 하면 수수료 차감 후 반환한다. 어느 방식이든 **거래가 어그러지면 몰수된 자금은 정상적으로 이행한 상대방에게 보상**으로 돌아간다. 그리고 **누구도 로그인 없이 대시보드를 볼 수 없으며, 회원가입은 불가능하고 법인이 발급한 계정만 접근**할 수 있다.

## 1. 용어 & 역할 (Glossary)

| 기호/용어 | 의미 |
|---|---|
| **A** | 일반적으로 **크립토(USDT) 제공자 / 판매자(Maker)**. 자산을 에스크로에 예치하는 쪽. |
| **B** | 일반적으로 **법정화폐(원화 등) 제공자 / 구매자(Taker)**. 오프라인으로 송금하는 쪽. |
| **법인 (LLC)** | 플랫폼 운영 주체 = **Wyoming LLC**. Mode 1에서 3번째 멀티시그 키 보유자이자 중재자. |
| **공동 지갑 (Joint Safe)** | Mode 1에서 거래 1건마다 생성되는 2-of-3 Gnosis Safe. owners=[A, B, LLC], threshold=2. |
| **보증금 (Bond)** | Mode 2 오프라인 거래에서 양측이 거는 USDT 담보. 신의성실 보증. |
| **USDT** | 기본 정산 자산(Tether). USDC도 보조 지원. |
| `feeRecipient` | 플랫폼 수수료 수취 주소. 프로덕션에서는 `FeeDistributor`(3-of-5 멀티시그). |
| `ARBITRATOR_ROLE` | 분쟁 중재 권한. Mode 2 컨트랙트 / Mode 1 법인 키. |
| `KEEPER_ROLE` | 데드라인 만료 등 자동화 트리거 봇 권한 (Mode 2). |

## 2. 거래 처리 방식 개요 (Two Modes)

플랫폼은 **두 가지 정산 아키텍처**를 지원하며, 거래 생성 시 **유저 또는 어드민이 방식을 선택**한다.

```
                         ┌─────────────────────────────────────────┐
   거래 생성 (A·B 매칭)  │  방식 선택 (유저 또는 어드민)             │
                         └───────────────┬─────────────┬───────────┘
                                         │             │
                  ┌──────────────────────▼──┐   ┌──────▼─────────────────────┐
                  │ Mode 1                    │   │ Mode 2                      │
                  │ 2-of-3 공동 멀티시그      │   │ 보증금 기반 하이브리드      │
                  │ (대외 표준 / 기본 노출)   │   │ (내부 옵션)                 │
                  └───────────────────────────┘   └─────────────────────────────┘
```

**대외 인식 정책**: UI·마케팅·기본값에서는 **거의 항상 Mode 1(멀티시그)** 을 쓰는 것처럼 보이게 한다. Mode 2는 어드민/특정 거래에서만 노출되는 내부 옵션으로 취급한다. (단, 두 방식 모두 실제로 동작해야 하며 감사 대상이다.)

> **결정 D1**: 에스크로 성격 = **하이브리드** + **2개 모드 병존**, 대외 기본은 Mode 1.

## 3. Mode 1 — 2-of-3 공동 멀티시그 에스크로 (대외 표준)

### 3.1 구성

- 거래 1건마다 **전용 Gnosis Safe** 를 생성한다 (Safe Factory).
- **owners = [A, B, LLC], threshold = 2** → 출금에는 서로 다른 2개의 서명이 필요.
- 거래 자산(USDT)은 **판매자 A가 이 Safe로 직접 입금**한다. (B는 자산을 온체인에 넣지 않고, 법정화폐를 오프라인으로 보낸다.)
- **법인은 평시에 자금에 손대지 않는다.** 키 1개로는 아무것도 출금할 수 없다 → **비수탁(non-custodial)에 준함.**

### 3.2 정상 흐름 (Happy Path)

```
 1. A·B 매칭 성립
 2. 공동 Safe 생성 (owners=[A,B,LLC], threshold=2)
 3. A → Safe : USDT 예치
 4. B → A    : 원화 등 법정화폐 송금 (오프라인, 체인 밖)
 5. A 서명 + B 서명 (2/3)  ──►  Safe가 USDT를 B에게 전송
                                 + 플랫폼 수수료를 feeRecipient로 전송 (동일 배치 tx)
    ※ 법인은 서명하지 않음. 자금에 일절 관여 안 함.
```

### 3.3 분쟁 흐름 (Dispute Path)

```
 시나리오: B가 원화를 보냈는데 A가 USDT 출금 서명을 거부하고 버팀.

 1. B → 법인에 "중재 요청" (증거 첨부: 송금 영수증 등 → IPFS 해시)
 2. 법인이 증거를 검토하여 B가 정당하다고 판단
 3. 법인 서명 + B 서명 (2/3)  ──►  A의 동의 없이 USDT를 B에게 안전하게 전송

 반대 시나리오: B가 거짓으로 "보냈다"고 주장 (실제 미송금)
 → 법인이 A 편으로 판정 → 법인 서명 + A 서명 (2/3) → USDT를 A에게 환불
```

> **신뢰 포인트(외부에 강조할 메시지):** 법인은 키 1개뿐이라 **단독으로 자금을 빼낼 수 없다.** 정상 거래에선 법인이 서명조차 하지 않으며, **분쟁 시에만 "캐스팅 보트"** 로 개입해 정당한 쪽 편을 든다.

### 3.4 수수료 징수 방식 (Mode 1)

- 출금 트랜잭션은 **배치(batch)** 로 구성한다: `USDT → 수령자` + `수수료 → feeRecipient`.
- A·B(정상) 또는 법인+한쪽(분쟁)이 서명하는 **그 트랜잭션 안에 수수료 출력이 명시**되므로, 서명자가 수수료 금액을 검증한 뒤 서명한다.
- 대안: 입금 시점 선공제(미선호 — Safe 단순성 해침). **기본은 출금 배치 내 수수료 출력.**

> **결정 D9 (OQ-1 해소)**: 수수료 **부담 주체는 거래(pool)별로 다르다.** Pool 생성 시 생성자가 **"내가 낸다(pay)" vs "상대에게서 받는다(receive)"** 를 선택한다. 출금 배치는 그 선택에 따라 수수료 출력을 구성한다.

### 3.5 신뢰·보안 속성

- **검열·오출금 방지**: 법인 단독 출금 불가(2/3 필요).
- **법인 키 관리 (D11)**: **MPC 지갑(Fireblocks 등)** 으로 보관·서명. 키를 분산 생성(TSS)해 단일 노출 지점이 없고, 회전·정책 기반 승인·감사 로그가 용이하다. 운영비는 감수한다.
- **Safe 버전·가드**: 표준 Gnosis Safe + 검증된 모듈만 사용. 커스텀 모듈 최소화(감사 표면 축소).

### 3.6 엣지 케이스 (Mode 1)

| 케이스 | 처리 |
|---|---|
| A·B 둘 다 잠수(서명 안 함) | **데드라인 후 A(예치자)에게 환불 (D12).** A가 자산을 넣은 당사자이므로 만료 시 A 환불을 기본으로 한다. 트리거는 법인 키 + 타임락 모듈(데드라인 경과를 컨트랙트가 강제). |
| Safe 생성 가스비 | **A(생성자)가 부담 (D13).** Safe를 여는 A가 직접 가스비 지불. |
| 부분 정산 | **양 모드 지원 (D14).** Mode 1은 공동 Safe에서 체결분만큼 부분 출금(여러 번의 2/3 서명 트랜잭션)으로 처리. ⚠️ 부분 정산은 회계·분쟁·감사 복잡도를 키우므로 잔여분 추적을 명확히 설계한다. |

## 4. Mode 2 — 보증금 기반 하이브리드 에스크로 (내부 옵션)

Mode 2는 **거래 자산의 온체인 여부**에 따라 두 하위 경로로 나뉜다.

### 4.1 온체인 거래 → 원자적 정산 (Atomic Settlement)

> **결정 D4**: 온체인 거래의 성공 판정 = **원자적 정산**(별도 오라클 검증 불필요).

```
 1. A·B 매칭
 2. A → EscrowVault : 자산 A 예치
    B → EscrowVault : 자산 B 예치
 3. 양측 자산이 모두 예치되면(조건 충족), 컨트랙트가 한 트랜잭션에서
    동시에 교환:  A의 자산 → B,  B의 자산 → A,  수수료 → feeRecipient
    → 어느 한쪽이라도 미충족이면 전체 롤백 (원자성).
```

- 별도의 "성공" 버튼·오라클이 필요 없다. **조건 충족 = 자동 정산.**
- 한쪽만 예치하고 상대가 미예치 → 데드라인 후 **예치자에게 전액 환불**.

### 4.2 오프라인 거래 → 보증금 + 양측 서명

> **결정 D3**: 오프라인 정산 트리거 = **양측 모두 서명**.

```
 1. A·B 매칭
 2. A → EscrowVault : USDT 보증금 예치
    B → EscrowVault : USDT 보증금 예치   (양측 다 담보를 건다)
 3. 실제 거래(원화 송금 등)는 오프라인 진행
 4. A '완료' 서명  +  B '완료' 서명  (양쪽 다)
    ──► 수수료 차감 후 각자의 보증금을 각자에게 반환
 ※ 한쪽이라도 미서명 → §4.3로 진입 (데드라인 → 분쟁/만료)
```

- **보증금은 거래 자산이 아니라 신의성실 담보**다. 정상 종료 시 (수수료 차감 후) **건 사람에게 그대로 돌아간다.**
- **송금 확인 (D10)**: 정상 흐름은 **증빙 업로드 없이 상호확인**으로 종료한다 — B '송금함' + A '수령함' 서명이면 충분(영수증 IPFS 업로드 불필요). 단, 분쟁 진입 시에는 중재자가 **선택적으로** 증거를 요청·참고할 수 있다(필수 아님). ⚠️ 증빙이 강제되지 않으므로 분쟁 판정은 중재자 재량 비중이 커진다 — 이 리스크를 인지하고 운영한다.

### 4.3 디폴트 / 분쟁 처리 (Mode 2)

> **결정 D2**: 디폴트 시 몰수 보증금 = **정상 이행한 상대방에게 보상**.

```
 - 한쪽(예: A)이 약속을 어기거나 확인을 거부 → B가 증거 첨부해 분쟁 제기 (IPFS 해시)
 - 중재(ARBITRATOR_ROLE, 2-of-3) 판정:
     · 승자 = 정상 이행한 쪽
     · 패자의 몰수 보증금  ──►  대부분 승자에게 보상 지급
                              + 일부(penaltyFeeBps)는 플랫폼 페널티 수수료
 - 양측 다 무응답 → KEEPER가 데드라인 만료 처리 → 보증금 각자 환불(mutual refund)
```

### 4.4 수수료 (Mode 2)

## 5. 상태 머신 (State Machines)

### Mode 1 — Joint Safe Lifecycle
```
CREATED ──(A 입금)──► FUNDED ──(A+B 서명)──────────► RELEASED(완료)
                          │
                          ├──(분쟁 제기)──► DISPUTED ──(법인+정당측 서명)──► RESOLVED(완료)
                          │
                          └──(장기 무응답)► (동결, 법인 중재로만 해소)
```

### Mode 2 — Escrow Lifecycle
```
PENDING ──(양측 예치 완료)──► ACTIVE ──┬─(온체인: 조건충족)─────► COMPLETED (원자정산)
                                        ├─(오프라인: 양측 서명)──► COMPLETED (보증금 반환)
                                        ├─(분쟁 제기)──► DISPUTED ─(중재 판정)─► RESOLVED
                                        └─(데드라인 만료)──────► CANCELLED (환불)
```

| D13 | Safe 생성 가스비 | **A(생성자) 부담** |
| D14 | 부분체결(partial fill) | **양 모드 지원** (Mode 1은 부분 출금, 잔여분 추적 설계 필요) |
| D15 | 어드민 오버라이드 시점 | **분쟁 시에도 가능** (전 구간) — 감사 로그·전역 상한·중재 승인 강제 |

## 7. 수수료 & 보증금 모델 (거래별 설정)

> **원칙 (D7)**: 수수료·보증금은 **전역 고정 상수가 아니다.** 각 거래(pool)마다 금액을 설정하며, 어드민이 거래별로 직접 정하거나 오버라이드할 수 있다. 전역에는 **상·하한 가드(min/max)** 만 둔다. (현재 코드의 `PLATFORM_FEE_BPS=30` vs `relayFeeBps=50` 같은 전역 고정값 불일치는 이 모델로 대체된다.)

### 7.1 거래별 파라미터 (pool 생성 시 결정)
| 파라미터 | 설정 주체 | 설명 |
|---|---|---|
| **보증금(Bond) 금액** | 생성자 / 어드민 | 거래별로 지정. 어드민이 오버라이드 가능. |
| **거래 수수료 금액·율** | 생성자 / 어드민 | 거래별로 지정. 전역 max 상한 내. |
| **수수료 부담 주체 (D9)** | 생성자 | "내가 낸다(pay)" vs "상대에게서 받는다(receive)" 선택. |

### 7.2 전역 가드 & 페널티
| 항목 | 설명 |
|---|---|
| 전역 수수료/보증금 **상한(max)** | 어드민이 설정. 거래별 값이 이를 초과 못 함(사용자 보호·감사 경계). |
| **Penalty Fee** | 분쟁 패자 몰수분 중 플랫폼 몫(나머지는 승자 보상 — D2). 전역값 또는 거래별. |

### 7.3 변경·거버넌스
- **전역 상·하한 변경**: 48시간 타임락 + 3-of-5 멀티시그.
- **개별 거래값**: pool 생성 시점에 확정. 생성 후 변경 불가(불변)를 기본으로 한다(분쟁·감사 단순화).
- **어드민 오버라이드 시점 (D15)**: 어드민은 **분쟁 중재 단계에서도** 거래별 수수료·보증금·페널티 값을 조정할 수 있다. (예치 전~분쟁까지 전 구간 허용.)
- ⚠️ **거버넌스 리스크**: 분쟁 중 값 변경은 조작·자의성 여지가 크다. 따라서 **(1) 모든 오버라이드는 불변 감사 로그(누가·언제·전후값)로 기록**, **(2) 전역 max 상한 가드 내에서만 허용**, **(3) 분쟁 단계 변경은 중재 멀티시그 승인 필요** 를 강제한다.

## 8. 인증 & 접근 제어 (로그인 게이팅)

> **결정 D5**: 로그인 우선 · 회원가입 불가 · 법인 발급 계정만 접근.

### 8.1 요구사항 (하드 룰)
1. **로그인 우선**: 미인증 사용자가 어떤 경로(`/`, `/pools`, `/escrow`, `/admin` 등 전부)로 접근해도 **로그인 화면으로 강제 리다이렉트**. 대시보드/풀 목록 등 어떤 콘텐츠도 로그인 전에는 노출 금지.
2. **회원가입 불가**: 셀프 가입 경로 없음. "Sign up" UI/엔드포인트 미존재.
3. **법인 발급 계정만**: 어드민(법인)이 **사전 등록(allowlist)** 한 계정만 로그인 가능. 미등록 이메일/지갑은 인증 시도해도 거부.

### 8.2 권장 구현
- **라우트 가드**: Next.js **middleware** 로 전 경로 보호. 세션 없으면 `/login` 리다이렉트. `/login`·정적 자산만 예외.
- **인증 수단**: Privy(이메일/구글/지갑 등) **+ allowlist 강제**. Privy 로그인 성공 후 서버에서 allowlist 대조 → 미등록이면 세션 미발급 후 로그아웃.
- **계정 프로비저닝(어드민)**: 어드민 페이지에 "계정 발급" 기능 → allowlist에 이메일/지갑 추가·삭제. 역할(admin/maker/taker) 부여.
- **저장소 (D8 확정)**: **Supabase(Postgres)** 신설. `accounts`(이메일/지갑/역할/상태), `allowlist`, 그리고 향후 거래 메타·채팅·분쟁 증거 메타를 함께 둔다. 로그인 시 서버(또는 Edge Function)에서 Supabase allowlist를 대조한다. RLS(Row Level Security)로 역할별 접근 제한.

> **현재 상태와의 차이**: 지금은 `Web3Provider`에 하드코딩된 테스트 계정 선택 모달 + Privy 폴백 구조이며, **라우트 가드도 allowlist 강제도 없다.** D5 충족을 위해 미들웨어 가드 + allowlist 검증 + 어드민 프로비저닝을 신규 구현해야 한다.

3. **프론트–컨트랙트 온체인 연동 전무** (전부 mockData). wagmi read/write 훅으로 교체 필요.
